# SPEC.md — IISDeploySlotManager

> 요구사항 기반 설계 초안. 미구현이며 사용자 검토 대상이다.

## 1. 구성과 경계

- Proxy: 동일 코드로 IIS 또는 Windows 서비스에서 실행한다. 모드별 TLS·계정·포트 설정은 독립적이다. 노드별 운영 endpoint를 소유하는 인스턴스는 하나다. Active–Active 페어의 서로 다른 노드에는 각각 활성 Proxy가 있다.
- Admin: Proxy 및 업무 사이트와 독립된 관리 웹과 주소를 갖는다. 관리 웹은 Controller를 호출하며 특권 계정으로 임의 명령을 실행하지 않는다.
- Controller: Windows 서비스로 프로세스 소유 관계 조회·정상/한정 강제 종료, 파일 배포·설정 변환·암호화, 작업 큐·예약·IIS 관리·동기화·상태 reconciliation을 수행한다. 브라우저 연결 종료와 무관하게 진행한다. 취소 요청은 현재 단계의 안전 지점에서 반영한다. 권한은 설치 단계에서 전용 서비스 계정에 위임하고 실제 작업마다 검사한다.
- 웹↔Controller: Named Pipe IPC 우선, 연결 불가 시 인증된 로컬 HTTP 계열 API(기본 HTTPS)를 사용한다. 두 transport의 명령 계약·권한·작업 ID는 동일하다. 상세는 14절을 따른다.
- Blue/Green: 전용 사이트·App Pool·폴더를 각각 갖는다. 동일 서버 내부 통신은 루프백 HTTP를 기본 설계로 하고 백엔드 외부 직접 접근을 제한한다.
- 운영 주소는 활성 슬롯, 검증 주소는 고정 슬롯으로 라우팅한다. 검증 주소의 접근 정책·쿠키·리다이렉트·DNS·인증서 SAN을 확인한다.
- HA 페어 모드에서는 기존 Windows NLB 또는 로드밸런서가 두 노드로 트래픽을 분배한다. 각 노드에 Controller·Proxy·Blue/Green·로컬 SQLite·패키지 보관소를 둔다. 변경·작업 결과·파일은 전용 서비스 간 프로토콜로 동기화한다. SQLite의 로컬 잠금만으로 페어 실행권을 얻었다고 판단하지 않는다.

## 2. 기본 정보와 사이트 구성

입력: 솔루션 식별자, 운영/검증/관리 호스트명, 슬롯 사이트·풀 이름, 루프백 포트, TLS 인증서 참조, 관리·프록시 호스팅 정보, 슬롯/패키지/상태/백업 경로, 실행 계정 참조, 권한 매핑, 설정·점검·보존·중지·예약 정책. 페어에서는 페어 ID·상대 노드 ID·신뢰할 노드 인증 정보·관리/동기화 endpoint·지정 조정 노드·로컬 SQLite/패키지 경로·노드별 검증 주소·NLB/LB 상태 확인 방식을 받는다.

계획 단계에서 IIS/Hosting Bundle 등 선행조건, 이름/바인딩/경로 중복, 인증서·키 접근, 실행 계정, 디스크 공간, 보호 경로를 검사한다. 도구 소유 리소스만 생성·갱신하고 타 사이트·풀을 자동 인수하지 않는다. 같은 요청 반복은 멱등적이다.

기존 사이트 편입이 필요하면 차이·영향을 명시한 별도 계획으로 다루며 자동 강제 종료는 전용 풀 조건 충족 전 차단한다. 부분 생성 실패 시 생성한 리소스만 추적해 복구하고 기존 리소스를 삭제하지 않는다.

초기 관리 웹·Controller와 서비스 등록은 로컬 설치 절차로 부트스트랩한다. 웹에서 권한을 자동 상승시키거나 설치에 필요한 계정 비밀번호를 보관하지 않는다.

## 3. 인증·권한·감사

관리 웹 인증 모드는 Windows 또는 Entra ID 중 선택한다. Entra는 허용 조직과 앱 역할을 검증한다. Windows는 AD 그룹 SID 기반 권한 매핑을 사용한다. 업무 앱 인증은 변경하지 않는다.

역할: 조회, 배포·점검, 전환·롤백, 시스템 설정. 특별관리 계정의 용도와 권한을 따로 지정하며 서비스 계정·비상 복구 계정과 혼동하지 않는다. API와 Controller에서도 권한을 검사한다.

CSRF 보호, 변경 GET 금지, 안전한 출력 인코딩, 관리 API 접근 제한, 세션 정책을 적용한다. 인증/권한 변경은 새 로그인·권한을 검증하고 로컬 권한 기반 복구 경로를 유지한다. 실패 시 인증을 우회하거나 무인증 모드로 강등하지 않는다.

감사: 작업 ID, 로그인 주체와 실행 주체, 시각, 대상, 이유, 변경 전후 revision, 패키지 해시, 단계 결과, 종료/권한 오류, 모듈 버전을 기록한다. 비밀값은 수집하지 않거나 마스킹한다. 로그 ACL·보존·외부 백업을 적용하며 로컬 관리자에 대한 완전한 변조 방지를 주장하지 않는다.

## 4. 영속 작업과 배포

작업 상태는 Planned, PendingSync, Queued, Running(세부 단계), NeedsAdministrator, Blocked, Succeeded, Failed, Cancelled, RecoveryRequired로 관리한다. 양 모드 모두 노드별 SQLite에 상태·revision·단계 저널을 영속화한다. 페어 명령의 순서·승인은 지정 조정 노드가 확정하고 상대 저장 ACK를 동기화 기록에 연결한다. 관측/실행 결과는 해당 노드가 원본이다. 단순 행 병합이나 DB 파일 복사는 사용하지 않는다.

솔루션별 배타 실행, 호스팅 모드 전환의 노드별 배타 실행, 중복 요청 ID, revision 사전조건을 적용한다. 페어에서는 양쪽 웹의 요청을 지정 조정 노드가 직렬화한다. 노드 단독 SQLite 잠금이나 heartbeat로 페어 권한을 만들지 않는다. 재시작 시 미완료 작업을 실제 IIS/라우팅/파일 상태와 대조하며 불확실하면 재실행·재전환하지 않고 RecoveryRequired로 둔다.

배포 순서: 사전 검사 → 패키지 검증 → 현재 운영 릴리스의 복구 백업 확보 → 대기 슬롯 격리/중지 → 덮어쓸 대상의 변경 전 백업 생성·전체 검증 → 설정 분석·변환 → 파일 배치·암호화 → 기동·워밍업 → 자동/수동 점검. 백업/키 검증 실패 시 첫 파일 변경부터 차단하며 필수 점검 완료 전 전환을 허용하지 않는다. 예약 배포도 같은 백업 게이트를 적용한다. 상세는 15절을 따른다.

패키지는 불변 버전·해시·출처로 식별한다. ZIP 경로 탈출·재분석 지점·압축 폭탄·용량 초과·임의 삭제를 차단한다. 패키지/백업은 웹 루트 밖에 둔다. 배포 직전 대상이 비운영 슬롯인지 다시 확인한다.

검증은 패키지·설정·점검 프로필·모듈 revision에 연결한다. 하나라도 바뀌면 무효화한다. 전환은 RequestedRevision → AppliedRevision 확인 → 해당 Proxy를 경유한 노드/슬롯/릴리스 검증 → 관찰 통과 순으로 완료한다. DB 저장이나 라우팅 파일 갱신만으로 성공 처리하지 않는다. 이전 슬롯은 종료 대기·보존 정책을 유지하되 롤백의 원본은 백업 압축파일이다.

Controller는 등록된 루프백 destination/호스트만 포함하는 검증된 라우팅 snapshot을 원자적으로 게시한다. Proxy는 별도 ACL의 읽기 전용 snapshot을 읽고 실제 YARP 구성 적용 후 InstanceId·AppliedRevision·구성 해시·검증 결과를 인증된 로컬 상태 endpoint로 제공한다. 알림/파일 watcher 호출 자체는 적용 ACK가 아니다. reload 실패 시 이전 revision을 유지하고 Controller는 전환 실패/결과 불명으로 처리해 이전 슬롯 중지·덮어쓰기를 금지한다.

Proxy는 프로세스 재시작 시 별도로 영속화한 마지막 적용 완료 snapshot을 검증해 복원하며 Controller/SQLite 연결에 기동을 의존하지 않는다. 초기 유효 snapshot이 없으면 임의 라우팅을 만들지 않고 준비 실패로 표시한다. 재시작한 Proxy의 InstanceId가 바뀌면 이전 인스턴스 ACK를 재사용하지 않고 실제 요청까지 재검증한다. 관측 endpoint는 응답 캐시를 사용하지 않는다.

## 5. 정상 중지와 제한 시간 후 강제 종료

정상 중지 대상은 등록된 비운영 슬롯의 사이트와 전용 App Pool이다. 운영 라우팅 제거 확인, 검증 주소를 포함한 신규 요청 차단, 진행 중 요청 종료 대기, 정상 site/pool stop 요청, 상태·프로세스 종료 확인 순으로 수행한다. 검증 주소 차단은 배포 동안 유지한다. 긴급 인플레이스 복원은 15절의 명시적 복구 모드에서 대상 트래픽 차단 후에만 같은 중지 절차를 사용한다. 무조건 IIS 전체를 재시작하지 않는다.

DrainTimeout과 StopTimeout은 별도 유한 양수 값으로 받는다. IIS의 shutdownTimeLimit에 의한 종료도 고려하며 실제 적용값을 표시한다. 배포 대상 앱이 장시간 요청을 유지하면 설정한 종료 정책의 영향을 계획에서 표시한다.

기한 초과 후에도 프로세스가 남으면 실행 직전 다음 조건을 모두 재검증한다.

1. 대상 슬롯은 비운영 상태이며 변경 잠금을 소유하고 있다.
2. 풀이 다른 사이트/애플리케이션과 공유되지 않는다.
3. IIS가 보고한 풀→worker 연결과 PID·시작 시각/프로세스 식별이 일치한다.
4. 프로세스 종료 권한이 있다. ASP.NET Core out-of-process 자식은 소유 관계가 확인되는 경우만 처리하며 이름/포트만으로 추정하지 않는다.

권한과 소유 관계가 확인되면 해당 슬롯 프로세스만 강제 종료하고 종료·파일 잠금 해제를 다시 확인한다. 전체 w3wp/dotnet 일괄 종료, PID 재사용 대상 종료, 임의 프로세스 트리 종료는 금지한다. 접근 거부·미확인 소유 관계·종료 실패 시 파일 덮어쓰기를 시작하지 않는다.

NeedsAdministrator 또는 Blocked로 전환하고 관리자 화면에 지속 알림을 남긴다. 알림에는 작업·슬롯·풀·확인된 PID·경과 시간·이유·권장 수동 조치가 포함되고 비밀값은 없다. 외부 알림은 수신·전송을 설정한 채널만 사용한다.

관리자 조치 후 확인/재개 기능은 실제 중지·대상·계획 revision을 재검사한다. 알림 확인만으로 실행하거나 무한 권한 재시도하지 않는다. 강제 종료로 중단된 요청 가능성을 감사에 남긴다.

## 6. 설정 분석·보호·암호화

대상은 JSON(appsettings 및 환경별 override), XML(web.config·별도 XML). JSON 중첩·배열과 JSONC, XML 네임스페이스·속성·외부 참조를 인식한다. 외부 엔터티/DTD 네트워크 접근을 허용하지 않는다.

파일 정책: Preserve(도구의 덮어쓰기·삭제 금지), ManagedMigration(버전 규칙에 따른 변환), Replace(패키지 기준 교체). 보호 규칙은 정규화된 경로와 실제 파일 범위에 적용한다.

신·구 스키마와 명시된 매핑으로 필수값·기본값·이름·자료형·단위 변경을 분석한다. 배열 병합이나 삭제 의미를 추측하지 않는다. 의미 불명/규칙 없음/보호 규칙 충돌/외부 변경은 전환을 차단한다. 적용 계획은 비밀값을 노출하지 않는다.

암호화 프로필은 파일·섹션/키 범위, 모듈 버전, 키 참조, 실행 주체, 판별·변환·암호화·검증 단계를 정의한다. 중복 암호화를 방지한다. 실제 슬롯 계정에서 앱이 읽는 것을 검사하고 암호화 필수 항목 실패 시 전환을 차단한다. JSON·임의 XML의 자동 복호화를 가정하지 않는다.

복호화가 필요한 분석은 등록 모듈을 통하며 관리 웹으로 평문을 반환하지 않는다. 평문 작업 파일이 필요한 도구는 제한 ACL·보관시간·실패/재부팅 후 정리를 정의하며 안전 삭제 보장을 주장하지 않는다. 암호화 키와 인증서 개인 키의 ACL·교체·복구를 별도 관리한다.

## 7. 점검 확장

솔루션별 프로필에 HTTP, PowerShell 7, 외부 실행 모듈, 수동 점검을 등록한다. 공통 결과: 항목 ID, Success/Failure/NotRun/Timeout, 필수 여부, 소요 시간, 마스킹한 상세, 슬롯·버전·설정·프로필 revision.

모듈 계약은 입력(슬롯 주소·버전·설정 참조), 출력(JSON 결과), 종료 코드, 제한 시간, 취소, 실행 계정, 파일/네트워크 허용 범위를 정의한다. 인자를 셸 문자열로 조합하지 않는다. 별도 프로세스는 샌드박스가 아니다. 모듈 변경은 기존 검증을 무효화한다.

솔루션의 SlotExecutionProfile에 Standby/Serving 모드, 모드 전달 키·설정 위치, BackgroundWorkPolicy, MigrationPolicy, 모드 확인 점검을 등록한다. 앱 또는 등록된 외부 스케줄러가 Standby에서 배치·큐 소비·메일 발송·자동 DB 마이그레이션을 억제한다는 계약을 검증해야 워밍업할 수 있다. 선언만으로 앱 동작을 억제했다고 간주하지 않는다. 해당 기능이 없는 앱은 부작용 없는 기동임을 점검 프로필로 명시하며 불명확하면 기동 전 차단한다.

YARP 라우팅 전환은 앱의 백그라운드 작업 리더 권한을 부여하지 않는다. Singleton 작업의 소유권/인계는 앱 또는 기존 스케줄러의 별도 계약으로 확인한다. 일반 배포·검증·복원 도중 DB 마이그레이션을 자동 실행하지 않는다. 운영 데이터를 변경하는 점검은 명시적으로 분류하고 기본 자동 점검에 포함하지 않는다. 필수 미실행·실패·타임아웃 시 전환을 차단한다.

ObservationProfile에는 최소 관찰 시간(유한 양수), 필수 점검 연속 성공 횟수, 점검 주기/제한 시간, 허용 연속 실패 수, 오류율/지연 기준과 최소 표본 수, 무트래픽 때의 합성 점검을 지정한다. 값이 비어 있거나 수집 불가·표본 부족이면 판정 불가로 보류한다. 경유 릴리스 불일치는 즉시 실패다. A 관찰 통과 전 B를 전환하지 않는다. 실패 시 B 전환을 중단하고 8절의 백업 복원 작업을 생성하며 검증을 생략한 무한 자동 복원을 하지 않는다.

## 8. 백업 압축파일 롤백과 특정 버전 재배포

롤백은 배포 전에 생성한 검증된 백업 압축파일을 선택해 앱 파일과 지정 설정을 복원하는 작업이다. 이전 슬롯을 가리키도록 라우팅만 되돌리는 동작은 임시 트래픽 복귀이며 롤백 완료로 기록하지 않는다. 원칙적으로 백업을 비운영 슬롯에 복원·점검한 뒤 트래픽을 전환한다. 긴급 시에는 대상 트래픽을 차단하고 중지한 사이트의 파일을 직접 덮어쓰는 인플레이스 복원도 명시적 복구 계획으로 제공한다.

백업 manifest로 파일 교체·추가·삭제와 설정 복원 범위를 계산하고 지정된 보호 파일 예외만 적용한다. appsettings/web.config의 특정 항목을 현재 값으로 유지하려면 백업 릴리스와 호환되는 복원 프로필을 명시해야 하며 묵시적으로 구·신 설정을 섞지 않는다. Preserve 파일은 명시적으로 검토된 복원 예외가 없으면 덮어쓰지 않고 충돌 시 차단한다. DB·사용자 파일·외부 부작용은 복원 범위가 아니다.

특정 버전 재배포는 원본 배포 패키지/검증된 완성 릴리스를 선택하는 별도 작업이며, 변경 전 백업·설정 호환성·암호화·점검을 다시 수행한다. 백업과 패키지의 종류·대상 노드/솔루션·기준 릴리스를 구분한다. 백업 키/내용을 실제 읽을 수 없으면 복구 가능으로 표시하지 않는다. 관리자 웹과 로컬 긴급 복구 절차는 15절 및 RECOVERY.md를 따른다.

## 9. 예약 대기 슬롯 자동 배포

옵션은 기본 꺼짐이다. 관리자가 고정 패키지 버전·해시, not-before 시각, 시간대, 대상 솔루션, 보존 조건을 지정한다. 날짜만 입력하면 선택 시간대의 해당 날짜 00:00 이후로 해석하고 UI에 정확한 시각을 보여준다. 내부 저장은 UTC와 원래 시간대를 함께 기록한다.

예약은 Controller가 영속 실행한다. 브라우저 종료·관리 웹 재활용에 영향을 받지 않는다. 재부팅으로 시각을 놓치면 복구 후 기한이 지난 작업을 한 번 재평가한다.

실행 시 현재 비운영 슬롯을 판별한다. 예약 때의 역할이 바뀌어도 운영 슬롯은 건드리지 않는다. 대상 버전·설정 정책이 이미 적용된 슬롯은 NoOp로 기록한다. 최신 버전을 임의 선택하거나 예약 승인 후 패키지·규칙 변경을 묵인하지 않는다.

실행 조건: 경합 작업 없음, 현재 라우팅·revision 확인, 롤백 보존 기간 충족, 복구 자료 보존 완료, 충분한 공간·권한·모듈·키 접근. 충족하지 못하면 보류/차단 이유와 다음 평가 상태를 표시한다. 운영 상태가 불명확하면 실행하지 않는다.

설정한 시각이 지났어도 롤백 보존 정책을 우회하지 않는다. 권한 부족은 NeedsAdministrator로 두며 자동 승격·무한 재시도하지 않는다. 예약 수정/취소는 감사하고 실행 시작 후에는 안전 지점에서만 취소한다. 자동 배포는 자동 운영 전환을 포함하지 않는다.

페어 예약은 단일 예약 ID·revision으로 양쪽 SQLite에 동기화하고 지정 Coordinator만 시작할 수 있다. 상대의 영속 수신 확인과 단계별 실행 허가 후 양쪽 대기 슬롯을 순서대로 갱신한다. 노드별 대상·성공 상태를 저장해 인계 시 완료 단계를 중복 실행하지 않는다. 조정 노드 접근 불가·미동기화·상대 ACK 부재 시 예약을 보류하며 타임아웃 승격으로 실행하지 않는다. 암호문·보호 키·고정 패키지의 실행 노드 접근을 사전 검사하며 비밀 접근 실패 시 우회하지 않는다.

## 10. 호스팅 전환·모니터링·외부 계약

IIS/Windows 서비스 모드 전환은 노드별 배타 잠금과 페어 조정 아래 인증서·개인 키 ACL·바인딩 충돌·실행 계정을 검사한다. endpoint 소유권을 인계하고 기동·HTTPS·라우팅을 확인한다. 실패하면 이전 모드 복구를 시도하며 복구 실패는 긴급 알림과 RecoveryRequired로 기록한다. 사이트 배포와 달리 무중단 보장을 하지 않는다.

관리 화면은 실제 확인 시각과 stale 상태를 표시한다. 모니터링 값 수집 실패를 정상 0건으로 표시하지 않는다. 요청 수·오류율·지연·디스크·키/인증서 만료·예약/작업 상태·프로세스 상태를 관측하고 외부 수집 연동은 별도 설정으로 둔다.

CLI는 --help, --version, --dry-run, --json을 지원한다. 종료 코드 0=성공/NoOp, 1=실행 실패·차단, 2=입력 오류. 웹은 작업 ID와 상태 조회를 제공하며 시작 응답을 작업 성공으로 간주하지 않는다. dry-run은 변경·종료·모듈 실행 없이 계획과 확인 가능한 권한 한계를 표시한다.

## 11. 암호화 압축 패키지와 DB 암호 보관

업로드 → LocalReceived → PendingPassword/LocalVerified → PeerPersisted → ContentVerified → PairReady 또는 Rejected 흐름을 제공한다. 단독 모드는 LocalVerified를 배포 준비로 사용하고 페어에서는 PairReady만 사용한다. 한 노드의 업로드 완료만으로 페어 Ready를 표시하지 않는다. 압축 형식/암호화 알고리즘 지원표는 구현 전 확정하며 첫 검토 후보는 AES 암호화 ZIP이다. 파일 확장자나 암호 입력 성공만으로 지원/무결성을 판단하지 않는다. 미지원 형식은 대상 서버 변경 전에 거부한다.

한쪽 웹에서 업로드를 완료하면 사용자에게 상대 업로드를 다시 요구하지 않고 Controller가 원본 암호화 파일·manifest의 자동 전송을 큐에 등록한다. 상대에도 로컬 패키지 사본을 보관한다. 수신 노드에 암호화 파일만 먼저 복제할 수 있지만, 암호 확인·무결성·수신 비밀 복호화가 끝나기 전에는 배포하지 않는다. 어느 노드가 업로드를 받았든 SourceUploadId/PackageId와 해시를 유지하고 조정 노드가 승인 revision을 확정한다. 상대 단절/용량/인증 오류는 ReplicaPending/ReplicaFailed로 표시하고 허용된 재시도만 수행한다. 명시적 단독 복구 절차 없이 복제 실패를 무시한 페어 배포를 허용하지 않는다.

HTTPS로 암호를 수신하고 제한 ACL의 격리 작업 공간에서 전체 항목을 스트림 검증한다. 헤더만 읽거나 일부 파일만 열어 암호 확인을 완료하지 않는다. 항목별 무결성, 중복/모호한 경로, 압축 전후 용량·개수·시간 제한, 경로 탈출·재분석 지점, 패키지 manifest를 확인한다. 암호화는 발행자 신뢰나 악성 코드 부재를 보장하지 않는다. 출처 검증은 별도로 유지한다.

원본 암호화 압축파일은 불변 패키지 ID·버전·해시로 보관한다. LocalVerified/PairReady 이후 파일을 바꾸면 새 패키지로 취급한다. 관리자 화면은 암호 입력/재검증 상태·노드별 파일 수신/검증 상태와 오류만 제공하고 저장된 암호를 재표시·다운로드하지 않는다. 암호 확인 API는 권한·속도 제한·CSRF를 적용하며 자동 추측이나 다른 저장 암호의 순회 시도를 하지 않는다.

검증 성공 후 로컬 SQLite에는 PackageId, SecretRevision, 대상 NodeId, 암호문, 보호 방식/키 버전 참조, 검증 시각·주체·상태를 저장한다. 암호를 해시만 저장하면 재배포에 사용할 수 없으므로 인증된 암호화/보호 API를 사용한다. 자체 암호 알고리즘은 만들지 않는다. 패키지 암호와 노드 인증 비밀·업무 설정 암호화 키는 별도 비밀이다.

루트 보호 키는 비밀 암호문과 같은 DB에 평문 저장하지 않는다. 수신 노드의 등록된 공개 키/표준 envelope 암호화로 수신자 전용 비밀을 전달하고 수신 Controller가 자기 로컬 보호 정책으로 저장한다. 개인 키·컴퓨터/계정 한정 DPAPI 암호문을 그대로 복제해 사용 가능하다고 가정하지 않는다. 전송·보관 모두 평문 암호를 노출하지 않으며 표준 암호 라이브러리/보호 API를 사용한다. 수신 노드별 키 교체·이전 키 보존·인증서 사본·복구를 검증한다. 키 손실은 저장 암호와 과거 패키지를 복구 불가능하게 할 수 있다.

복호화 권한은 Controller의 필요한 실행 경로로 한정하며 일반 조회자에게 주지 않는다. 작업별 패키지 ID·승인 revision에 바인딩하고 키/DB/복호화 오류는 명시적으로 차단한다. 암호를 URL, 프로세스 인자, 환경 변수, 로그·감사·브라우저 영속 저장소·모듈 stdout으로 전달하지 않는다. 외부 도구가 필요하면 안전한 IPC/입력 전달을 지원하는 도구만 허용한다.

평문 추출 자료는 격리 경로와 최소 ACL로 관리하고 실패/재부팅/취소 시 정리한다. 패키지 암호 레코드는 해당 패키지·예약·복구 자료의 참조가 남아 있으면 자동 삭제하지 않는다. 암호·키 변경은 revision을 올리고 예약/복구 가능성을 재검증한다. 복호화/오류 감사에는 비밀값을 포함하지 않는다.

차등 패치라면 manifest에 정확한 기준 릴리스/파일 해시, 추가·교체·삭제 목록을 둔다. 적용 전 일치 여부와 보호 파일 충돌을 확인한다. 누락 파일을 삭제 요청으로 해석하지 않는다. 기준 패키지/패치 체인 또는 완성된 복구 릴리스를 보존하며 역패치를 추측하지 않는다. 특정 버전 재배포와 양 노드 동일 결과를 복원할 수 없으면 LocalVerified/PairReady 배포 대상으로 승인하지 않는다.

## 12. Active–Active HA 페어

HA 노드 A/B와 노드 내부 Blue/Green은 별개 축이다. A/B는 둘 다 트래픽을 받을 수 있으며 각자의 활성 슬롯은 다를 수 있다. 페어 등록은 상호 인증·명시적 신뢰 등록으로 수행한다. IP/호스트명·상태 API 응답만으로 상대를 신뢰하지 않는다. 관리 통신은 인증된 TLS 채널로 제한하고 명령에 페어/노드/작업/릴리스/revision/실행권 세대를 포함한다.

Active–Active는 사용자 트래픽 방식이며 배포 조정은 등록 시 지정한 단일 Coordinator가 담당한다. 어느 웹에서든 변경/업로드를 요청할 수 있지만 비조정 노드는 제안을 전달하고 조정 노드가 base revision·권한·작업 충돌을 검사해 순서를 부여한다. 같은 설정의 동시 변경은 revision 충돌로 되돌리며 timestamp last-write-wins를 사용하지 않는다.

정상 페어 모드의 조정 명령은 페어/멤버십 revision, Coordinator 세대, 작업/단계 ID를 포함하고 현재 멤버 양쪽 로컬 DB의 durable ACK 후 실행 가능해진다. 단계별 실행 허가는 이전 결과 대조·양쪽 준비 확인 후 발행하며 수신 노드는 한 번만 소비하고 직전 권한/상태를 확인한다. ACK/결과가 불명확하거나 통신이 끊기면 다음 변경을 보류하고 실행 중인 비원자적 단계는 안전 지점에서 상태를 기록한다. 이미 시작한 단계의 순간 중단·글로벌 원자성을 주장하지 않는다.

계획된 조정 세대 변경은 양쪽 동의·영속 기록과 기존 조정 역할 해제 후 수행한다. 장애 인계는 기존 노드의 전원 차단 또는 Controller/복구 실행기의 중지·자동 재시작 방지 등 실제 변경 실행 차단을 관리자가 확인한 뒤 진행한다. 방화벽/명령 채널 단절만으로 실행 차단을 인정하지 않는다. 생존 노드에 증빙·작업자·사유를 남기고 고장 노드를 제외한 새 MembershipRevision/CoordinatorEpoch와 DegradedMaintenance 상태를 영속화한다. 고장 노드의 ACK를 요구하는 정상 페어 명령과 구분한다.

DegradedMaintenance에서는 예약·신규 페어 배포를 중지하고, 로컬 백업 복원·라우팅 복구·진단만 명시적으로 허용한다. 조정 노드가 고장 났어도 기존 작업과 충돌하지 않는 것이 확인된 로컬 긴급 복원은 15절의 복구 잠금/정지 조건으로 수행할 수 있다. 새 버전 배포를 재개하려면 상대 노드 교체/복구·강제 동기화·양쪽 기동 검사로 정상 페어를 재구성해야 한다.

구노드가 돌아오면 자동 등록/실행하지 않고 격리한다. 재등록 시 새 세대·현재 기준 데이터로 재동기화하고 기존 작업 허가·예약 실행권을 폐기한다. 통신 단절·heartbeat만으로 자동 승격하지 않으며 두 노드만으로 단절 중 자동 failover와 양쪽 쓰기의 안전성을 동시에 제공하지 않는다.

배포 절차:

1. 두 노드의 멤버십·연결·패키지/암호/키 접근·설정·활성 슬롯·복구 가능성을 검사하고 페어 작업을 생성한다.
2. A의 대기 슬롯 배포/점검, B의 대기 슬롯 배포/점검을 수행한다. 양쪽의 대상 릴리스·설정 정책·점검 revision이 준비되어야 전환할 수 있다. 환경 고유 설정은 노드 간 파일 해시 일치를 강제하지 않고 정책 준수를 검사한다.
3. 노드별 고정 검증 주소로 각각 확인한다. LB가 임의 노드로 보내는 공통 검증 주소만으로 양쪽 검증을 완료하지 않는다. 각 응답/결과에는 노드·슬롯·릴리스 식별자를 포함한다.
4. 반대 노드의 서비스 건전성을 확인하고 A를 전환·관찰한다. 성공 후 B를 전환·관찰한다. 노드별 이전 슬롯과 실제 라우팅 결과를 보존한다.
5. 실패하면 다음 노드 변경을 중단한다. 부분 성공·혼합 버전을 명시하고 백업 압축파일로 이전 릴리스를 복원·점검한 뒤 전환 완료 노드 복귀를 수행한다. 필요시 검증된 기존 슬롯으로 임시 트래픽 복귀는 가능하지만 백업 롤백 완료와 구분한다. 데이터 호환성/복원이 불확실하면 서비스 가능한 노드를 유지하며 관리자 복구로 넘긴다.

글로벌 동시 전환/분산 원자성은 제공하지 않는다. 구·신버전의 DB/세션/인증 키/외부 메시지 호환성과 일시적 혼합 서비스 허용 여부를 사전에 점검한다. 호환되지 않는 릴리스는 일반 순차 무중단 전환을 차단하고 별도 점검 작업으로 다룬다. 노드 간 세션 공유 또는 서비스 요구에 맞는 affinity는 기존 LB/앱과 함께 검증한다.

일반 LB는 HTTP(S) readiness probe가 Proxy 기동만이 아닌 현재 운영 앱의 실제 건전성을 반영하는지 검증한다. Windows NLB는 자체 애플리케이션 상태 검사를 제공한다고 가정하지 않는다. NLB 환경은 별도 감시→허용된 앱/노드 트래픽 제외→상태 확인→복구 후 재편입 계약이 필수다. 해당 연동이 없으면 자동 장애 제외 미지원으로 표시하고 관련 호스팅 전환/인플레이스 복원은 수동 제외 확인 전 차단한다.

페어 등록만으로 트래픽 HA를 생성하지 않는다. 필요할 때 설정된 연동으로 대상 범위를 drain하고 효과를 확인한다. 같은 NLB 노드가 다른 솔루션도 서비스하면 임의 호스트 전체 DrainStop을 수행하지 않는다. 연동 권한/상태가 없으면 관리자 조치로 차단한다. 기본 슬롯 전환은 해당 노드 YARP 라우팅만 변경하며 검증 주소·직접 바인딩의 우회 접근도 배포/복원 잠금에 포함한다.

NLB/LB는 유지하면서 제어 경로가 끊겨도 Proxy는 마지막 유효 라우팅으로 기존 서비스한다. 양쪽 로컬 DB·패키지 보관소·키를 복구할 수 있어야 한다. 노드 양쪽에서 동기화된 revision·패키지 해시·비밀 복호화와 키 복구를 확인한 후 준비 완료로 표시한다. 이 도구의 동기화는 관리 데이터·암호화 패키지에 한정하며 업무 DB·사용자 업로드·임의 파일시스템 HA를 구현하지 않는다.

관리 화면에는 노드별 상태·실측 시각·stale 여부·슬롯·버전·전환 단계·부분 실패·패키지/키 사용 가능성과 페어 작업을 표시한다. 상대 접근 불가와 중지는 구분한다. 페어 해제·노드 교체는 실행 중 작업을 정리하고 기존 노드의 명령 권한을 폐기한 뒤 새 멤버십 revision으로 등록한다.

## 13. 노드별 SQLite와 전용 동기화 프로토콜

별도 DB 서버 없이 각 노드 로컬 디스크의 SQLite를 사용한다. Controller가 유일한 DB 접근 경계이며 웹/Proxy/상대 노드는 DB 파일을 직접 열지 않는다. Controller 내부 쓰기는 짧은 트랜잭션으로 직렬화하고 busy 제한·취소·용량·무결성·마이그레이션 실패를 처리한다. .NET SQLite provider는 구현 때 최소 의존성으로 선정한다. DB 파일 ACL을 서비스·백업 주체로 제한하고 SQLite 자체가 암호화를 제공한다고 가정하지 않는다.

동기화 대상은 솔루션/슬롯 정의, 승인된 설정/보호/점검 프로필, 패키지 manifest·암호문 참조, 페어 멤버십·조정 세대, 작업·예약·감사/관측 이벤트다. 노드별 실제 경로·PID·키 ACL·계정/인증서 비밀과 원본 관측 상태를 다른 노드 값으로 덮어쓰지 않는다. 설정 동기화와 실행 시스템 설정 적용은 분리한다. 수신만으로 IIS·프로세스·업무 파일을 변경하지 않는다.

프로토콜은 인증된 HTTPS 위의 버전 있는 전용 애플리케이션 메시지/파일 전송 규약으로 구현한다. 자체 TCP 암호화·압축·범용 DB 복제 엔진을 만들지 않는다. 노드 간 mTLS와 명시적 페어 신뢰 목록, 방화벽 범위를 적용한다. 인증서 교체·폐기·만료와 프로토콜/DB 스키마 버전 협상을 처리하고 미지원 버전은 부분 적용하지 않는다.

메시지 공통 필드: ProtocolVersion, PairId, MembershipRevision, SenderNodeId, CoordinatorEpoch, MessageId, OriginSequence, EntityId, BaseRevision, EntityRevision, Operation, PayloadHash. 로컬 경로는 받지 않고 등록 ID로 대상 리소스를 해석한다. 명령/파일 전송의 크기·시간·인증 주체·권한·리플레이·revision을 검증한다.

로컬 변경과 outbox 이벤트는 동일 SQLite 트랜잭션에 기록한다. 수신은 inbox 중복 검사·데이터 반영·수신 cursor를 같은 트랜잭션에 저장한 후 durable ACK를 전송한다. 중복 전송은 같은 MessageId 결과를 반환하며 잘못된 순서·누락 sequence는 재요청/재동기화한다. 서로 다른 내용의 같은 ID나 revision은 충돌로 격리한다. at-least-once 전달과 멱등 처리를 사용하며 네트워크 exactly-once 실행을 약속하지 않는다.

정보 동기화 상태는 LocalPending(제안 임시 보관), PendingSync, PeerPersisted, Synced, Conflict/Rejected로 구분한다. 패키지 상태는 11절의 LocalReceived/LocalVerified/PairReady와 노드별 복제 상태로 구분한다. 상대가 실제 영속 보관하고 패키지 전체·수신 비밀 사용을 검사하기 전에는 PairReady나 페어 승인 완료로 표시하지 않는다. 상대와 단절돼도 임시 업로드·관측 조회는 가능하나 페어 설정 효력·예약·배포 시작은 보류한다. 시간순 자동 병합은 하지 않는다.

같은 설정의 동시 변경은 조정 노드의 base revision 검사로 충돌 처리하고 사용자에게 재검토를 요청한다. 노드별 관측/감사 이벤트는 원본 노드 ID+sequence로 append하며 동일 항목으로 병합하지 않는다. 삭제는 tombstone을 동기화하고 양쪽 확인·보존 참조 정리 후 실제 데이터를 제거한다. 오래된 오프라인 노드의 재등장으로 삭제 항목이 부활하지 않게 한다.

파일은 암호화 원본 archive/manifest의 콘텐츠 해시로 식별한다. 누락 블록 협상·이어받기·제한된 재시도·전송 속도/디스크 quota를 적용하고 chunk 해시와 최종 전체 해시를 검증한다. 임시 파일 수신 완료 후 로컬 보관소에 원자적으로 게시한다. manifest만 받거나 전송이 중단된 파일은 배포 대상으로 열지 않는다. 사용자 제공 파일명·경로로 임의 서버 파일을 요청/덮어쓰지 않는다.

패키지 암호는 11절의 수신 노드별 보호 envelope로만 동기화한다. 개인 키를 동기화하지 않는다. 페어 신규 등록/키 교체 후 비밀 수신·복호화 테스트가 끝나기 전 예약 실행 가능으로 표시하지 않는다. 암호·키 상태 revision은 패키지 파일 해시와 별도로 검증한다.

신규/장기 오프라인 노드는 승인된 논리 snapshot+기준 sequence를 수신한 후 변경 이벤트를 따라잡는다. snapshot에는 노드 전용 실행 상태를 덮어쓰지 않는 스키마와 검증 해시가 필요하다. 실행 중 DB/WAL/SHM 파일을 복사하거나 네트워크 공유 SQLite를 쓰지 않는다. snapshot 복구 중 배포를 시작하지 않는다.

SQLite 백업 API 등 일관된 백업을 사용하고 스키마 업그레이드 전 복구 지점을 보존한다. 양쪽 DB가 동기화됐다는 사실은 백업을 대체하지 않는다. 손상/삭제도 전파될 수 있으므로 별도 보존·키 복구·재등록 훈련을 둔다. 파괴적 스키마 변경은 양쪽 호환·유지보수 절차를 확인한 뒤 적용한다.

## 14. 웹↔서비스 IPC 및 HTTP 대체 경로

웹·CLI는 transport 중립 명령 클라이언트를 사용한다. 명령 종류는 계획 조회/검증, 등록된 작업 시작·취소·재개, 상태/감사 조회 등으로 제한한다. 임의 셸·SQL·파일 경로·PID kill 요청을 그대로 받지 않는다. 동일 명령 handler와 권한 검사를 Named Pipe와 HTTP가 공유한다.

기본 Named Pipe는 로컬 전용이며 서비스와 허용한 웹 App Pool/프로세스 계정만 ACL로 접근한다. 서버 소유 주체·상대 인증을 확인하고 원격 pipe 연결을 허용하지 않는다. 파이프 이름만 같다는 이유로 신뢰하지 않는다.

대체 HTTP API는 별도 로컬 endpoint를 사용하며 기본 루프백 HTTPS 바인딩과 명시적 클라이언트 인증을 적용한다. 인증서 신뢰를 검증하고 익명 호출·인증서 검증 우회를 허용하지 않는다. HTTP 계열 프로토콜을 사용한다는 것이 평문 전송을 허용한다는 뜻은 아니다. 노드 간 동기화 endpoint와 로컬 관리자 API는 listener·접근 정책·권한 범위를 분리한다.

IPC 연결 불가/미지원 오류만 대체 사유다. 인증 실패·권한 거부·잘못된 메시지는 HTTP로 우회하지 않는다. 실행 요청을 전송한 뒤 응답이 끊기면 먼저 동일 RequestId 상태를 대체 경로로 조회한다. 필요시 같은 RequestId로 재요청하며 새로운 ID로 중복 작업을 만들지 않는다. 양쪽 경로 실패 시 웹은 서비스 연결 불가를 표시하고 직접 IIS/SQLite/파일 변경으로 대체하지 않는다.

명령에는 RequestId, 솔루션/작업 ID, 예상 revision, 작업 사유, 인증된 사용자 식별/권한 문맥을 포함한다. RequestId는 호출 주체·실제 사용자·명령 종류·페어/대상·정규화 인자 해시와 결합한다. 같은 ID에 다른 내용/주체는 충돌로 거부하고 기존 결과를 노출하지 않는다. 동일 요청 재전송도 현재 상태 조회/작업 접근 권한을 재검사한다. 비밀값은 fingerprint에 포함해도 원문을 로그에 저장하지 않는다.

서비스는 transport 호출 주체를 검증하고 허용된 웹 서비스 주체가 전달한 사용자 문맥만 무결성 보호된 경로로 수용한다. 브라우저가 보낸 사용자 이름/역할 헤더를 권한 근거로 신뢰하지 않는다. 웹의 AD/Entra 토큰을 불필요하게 전달하거나 저장하지 않는다. 최종 리소스/작업 권한은 서비스가 검사한다.

긴 작업은 영속 접수 후 작업 ID를 반환하고 웹이 진행/결과를 조회한다. 접수·동기화 대기·실행·완료를 구분한다. 서비스 재시작에도 RequestId 중복 제거와 작업 상태를 유지한다. 오류 계약은 연결 실패, 인증 실패, 권한 부족, revision 충돌, 동기화 대기, 실행 실패, 결과 불명으로 구분한다.

서비스 계정은 IIS 구성·등록 슬롯 프로세스 종료·해당 폴더/키 접근에 필요한 권한을 설치 때 위임한다. 위임이 불가능한 작업에 높은 로컬 권한이 필요하면 설치 계획에 영향과 범위를 표시한다. 서버 관리자 권한이 있어도 도구의 대상·소유권·잠금 검사는 생략하지 않는다. 점검 스크립트는 별도 제한 계정으로 실행한다. 서비스를 고권한으로 실행한다는 이유로 웹/Proxy에도 같은 권한을 부여하지 않는다.

## 15. 배포 전 압축 백업과 긴급 수동 롤백

### 15.1 백업 생성 게이트

모든 수동/예약 배포와 복원은 첫 파괴적 변경 전에 백업을 생성·검증한다. 백업 종류는 CurrentServingRecovery(현재 운영 릴리스로 복귀)와 TargetBeforeOverwrite(덮어쓸 슬롯의 기존 상태)로 구분한다. 슬롯 버전이 다르면 하나의 백업을 두 목적에 재사용하지 않는다. 페어 각 노드의 실제 설정/파일이 다를 수 있으므로 노드별 백업을 생성한다. 빈 신규 슬롯은 EmptyBaseline manifest를 보존하며, 운영 이력이 없으면 이전 운영 버전 복구 가능이라고 표시하지 않는다.

운영 릴리스의 앱 코드/설정은 배포 잠금 동안 불변이어야 한다. 운영을 중지하지 않고 백업할 때는 파일 목록·내용 해시·설정 revision을 전후 확인하고 변경 감지 시 재시도 또는 배포 차단한다. 일관성을 확보할 수 없는 앱은 앱별 quiesce/스냅샷 절차를 요구하며 임의 파일 복사를 완료 백업으로 취급하지 않는다. 덮어쓸 대상은 5절대로 중지·잠금 확인 후 백업한다. 업무 DB·업로드·로그·공유 가변 데이터는 분리·제외한다.

백업은 전체 앱 파일 집합, 복원 프로필에 포함된 JSON/XML 설정, 해당 사이트/풀의 선언적 복구 설정(대상 범위만), 검증된 라우팅 snapshot 참조와 manifest를 압축 보관한다. manifest 필드: BackupId, Kind, NodeId, SolutionId, SourceSlotId, ReleaseId, CreatedUtc, ConfigRevision, 파일별 상대 경로/해시/크기/소유 정책, 키 참조/암호화 상태, 모듈/점검 버전, 복원 가능 대상. IIS 전체 설정·개인 키·평문 계정 자격증명을 자동 포함하지 않는다.

백업에는 설정 비밀이 있을 수 있으므로 암호화 압축과 인증된 manifest/해시, ACL을 적용한다. 암호/키는 11절의 노드별 보호와 별도 복구 보관을 사용한다. 압축 전체 읽기·해시·manifest·키 접근 검증을 완료한 후 Verified를 기록한다. 공간 부족·손상·불명확한 일관성·복구 키 없음은 배포 차단이다. 예약/보존 정책은 현재 복구점과 사용 중 백업/키를 자동 삭제하지 못한다.

페어 정상 배포는 각 노드의 백업이 로컬에 Verified이고 상대에 암호화 사본·복구 메타데이터의 영속 수신이 확인된 뒤 변경을 시작한다. 상대 파일 사본이 다른 노드 설정/암호문을 그대로 복원 가능하다는 뜻은 아니다. 동일 노드용 복원과 교체 노드 복원을 구분하고 후자는 키·계정·경로 재매핑/재보호가 검증되지 않으면 차단한다.

### 15.2 백업 압축파일 복원

관리자는 BackupId/압축파일과 대상 노드/솔루션/슬롯, 복원할 설정 범위, 작업 사유를 선택한다. 현재 manifest와 비교해 추가·교체·삭제·보호 충돌·필요 키·버전/데이터 호환성·서비스 영향의 계획을 제시한다. 정상 경로는 비운영 슬롯 복원이고, 긴급 인플레이스 복원은 대상 트래픽 제외·중지 확인과 별도 명시적 선택이 필요하다.

원본을 직접 덮어쓰기 전에 압축 전체를 격리 경로에서 검증하고 복원 직전 상태도 새 압축 백업으로 보존한다. 대상 루트/재분석 지점·권한·실제 PID를 재검사하고 파일 잠금 해제 후 manifest대로 복원한다. 백업에 없고 현재 릴리스의 관리 파일 집합에 속한 새 DLL 등은 정리 목록대로 제거한다. Preserve/사용자 데이터·타 솔루션 파일은 제거하지 않으며 미확인 파일 충돌은 차단한다. 사이트/풀 설정도 등록된 대상 범위만 적용한다.

백업에 이미 암호화된 설정은 그대로 복원하고 무조건 재암호화하지 않는다. 노드/계정/키가 달라 재보호가 필요하면 승인된 모듈과 키 접근을 검증한다. 앱·복원 설정 조합, Standby 부작용 억제, 기동·핵심 기능·실제 Proxy 경유 릴리스와 AppliedRevision·관찰을 통과해야 복원 완료다. 실패 시 임의 기동/트래픽 재편입·원래 배포 재개를 하지 않고 RecoveryRequired로 유지한다.

백업 복원은 관리 SQLite를 과거로 되돌리지 않는다. 현재 작업 이력에 복원 이벤트·실측 상태를 추가하며 DB/업무 데이터 스키마의 과거 호환성이 없으면 앱 파일만 복원해 해결된다고 표시하지 않는다. 완료해도 보류 예약·진행 중 배포를 자동 재개하지 않는다.

### 15.3 로컬 긴급 복구

관리 웹 장애는 로컬 CLI→Controller 경로로 복원한다. Controller까지 사용 불가하거나 관리 SQLite가 손상된 경우에 한해, 별도 설치한 로컬 Recovery 실행기가 offline restore를 수행한다. 이는 일반 웹의 직접 시스템 변경 fallback이 아니며 OS 관리자 권한·실물 백업·신뢰할 manifest·독립 키 접근과 운영자 작업 사유가 필요하다. DB·Entra/AD 로그인·상대 서버 ACK 없이도 로컬 압축 백업을 식별·검증할 수 있는 보호된 복구 메타데이터를 함께 보관한다. 비밀은 보안 입력/OS 키 저장소로 받고 CLI 인자에 넣지 않는다.

offline restore 시작 전 Controller를 중지하고 자동 복구/외부 스케줄러 재시작을 억제한 것을 확인한다. Controller와 Recovery 실행기가 공유하는 머신 전역 복구 잠금을 획득하고 서비스가 시작 시 반드시 확인하는 영속 RecoveryHold 표식을 생성한다. 동기화 수신·예약·기존 명령 replay도 보류한다. 실행 차단을 확인할 수 없으면 복원을 시작하지 않는다. 긴급 복원도 등록 대상·트래픽 차단·PID 검증·백업 검증을 생략하지 않는다.

활성 경로를 직접 덮어쓸 때는 대상의 NLB/LB 트래픽·YARP/직접/검증 주소를 차단하고 효과를 검증해야 한다. 관리자에게 수동 제외를 요청할 수 있으나 확인되지 않으면 진행하지 않는다. 해당 노드로만 접근하는 사이트라면 접속 공백을 계획에 명시한다. 로컬 복원은 상대 노드의 배포 권한을 탈취하거나 양쪽을 일괄 종료하지 않는다.

복구 실행기는 DB 외부에 무결성 보호한 append-only 복구 저널을 남긴다. Controller 재기동 시 RecoveryHold 상태에서 실제 파일·풀·라우팅·복구 저널과 SQLite를 대조해 이전 작업 허가를 무효화한다. 상대에 로컬 복구 사실을 전송해 필요한 강제 동기화/페어 복구를 완료한 후 관리자가 Hold 해제를 결정한다. 저널 대조와 세대 검사 전 예약·기존 outbox를 실행하지 않는다. 상세 운영 순서는 [RECOVERY.md](RECOVERY.md)를 따른다.

## 16. 관리자 강제 동기화와 데이터 불일치 복구

일반 증분 동기화로 해소되지 않는 SQLite의 공유 논리 데이터 불일치에 대해 관리자 강제 동기화를 제공한다. 이는 지정 소스의 선택 범위를 대상에 다시 적용하는 복구 작업이며 timestamp 최신 노드를 자동 정답으로 선택하지 않는다. 소스도 손상/오염될 수 있으므로 현재 서비스 실측 상태·감사·패키지 보유·revision/논리 해시를 비교해 운영자가 SourceNodeId, TargetNodeId, Scope, 사유를 명시한다.

권한은 시스템 설정/복구 역할로 제한한다. 범위는 공유 설정·보호/점검 프로필, 패키지/백업 catalog·암호화 파일/비밀 재전송, 보류 작업·예약의 복구 가능 정의, 논리 snapshot으로 구분한다. 노드 ID/로컬 경로/실행 계정/개인 키·실제 PID·Proxy의 실제 적용 상태는 덮어쓰지 않는다. 멤버십/조정 권한은 snapshot 내용으로 되돌리지 않고 12절의 별도 인계/재등록 절차로 처리한다. 감사·노드 관측 이력은 원본 provenance를 유지하며 대상 전용 기록을 삭제하지 않는다.

절차:

1. 양쪽의 신규 변경·예약·배포를 보류하고 실행 중 단계를 안전 지점까지 정리한다. 활성 배포 중이거나 소스/대상 revision이 바뀌면 계획을 무효화한다. 동기화는 기존 사용자 트래픽을 중지하지 않는다.
2. 양쪽 SQLite의 일관된 백업과 scope별 논리 snapshot·outbox/inbox/cursor·파일 catalog를 보존한다. 백업 검증 실패 시 대상 변경을 시작하지 않는다. 파일/비밀의 복원 필요 조건도 검사한다.
3. 소스 기준 추가·교체·논리 삭제와 잃게 되는 대상 전용 변경을 diff로 표시한다. 보호된 노드 전용 정보/감사 보존 및 예약 재활성화 차단을 계획에 표시하고 검토한 정확한 범위로 실행한다.
4. ForceSyncId·새 SyncGeneration·소스 기준 sequence·scope 해시를 고정한다. 검증된 논리 snapshot을 대상 staging에 수신한 뒤 선택된 공유 데이터만 로컬 SQLite 트랜잭션으로 반영한다. .db/WAL/SHM 복사·파일 덮어쓰기로 실행 DB를 교체하지 않는다.
5. 기준 sequence 이후 이벤트는 새 generation으로 재평가한다. 오래된 inbox/outbox/작업 실행 허가는 감사용으로 보존하되 replay를 격리한다. 기존 미완료 실행 결과는 별도 대조하며 복사된 작업/예약은 Paused/RecoveryRequired로 둔다. 과거 Succeeded 이벤트나 예약을 다시 실행하지 않는다.
6. 파일/백업은 콘텐츠 해시로 누락 사본을 전송·검증하고 비밀은 수신 노드용으로 재보호한다. 공유 scope의 논리 해시·revision·sequence와 참조 완전성을 확인하고 양쪽 durable ACK 후 Synced로 표시한다. 로컬 행 전체 해시는 노드 전용 정보가 다르므로 동일성을 강제하지 않는다.
7. 관리자 화면에 결과와 남은 차이를 표시한다. 설정 수신은 실제 IIS/프로세스/업무 파일 변경을 실행하지 않는다. 실제 상태가 원하는 설정과 다르면 별도 변경 계획으로 검증·적용한다. 예약/배포 재개는 관리자 결정과 revision·권한·상태 재검사를 거친다.

전송 중단은 같은 ForceSyncId로 이어받고 commit 후 응답 유실은 결과 조회로 확인한다. commit 전 실패는 staging 폐기/재시도, commit 후 불일치는 RecoveryRequired로 유지하고 보존 snapshot을 이용한 별도 취소 복구 계획을 제시한다. ACK가 없거나 상대가 단절되면 강제 완료 처리하지 않는다. 무한 재시도·양방향 덮어쓰기·인증 우회는 하지 않는다.

상대가 꺼져 있으면 소스 백업/전송 준비까지만 가능하고 완료는 재접속·인증·검증 후에만 기록한다. 고장 노드 복구/교체 시에는 격리와 새 멤버십으로 등록한 뒤 위 절차를 사용한다. DegradedMaintenance의 현재 노드에서 만든 로컬 복구 이력은 상대 snapshot으로 지우지 않는다. 강제 동기화는 백업 복원/조정 노드 승격을 대체하지 않는다.

## 17. 페어링 신뢰 설정과 통신 보안

추천 전송 기반은 Windows 서비스가 직접 종단하는 mTLS HTTPS다. SQLite 변경·명령·암호화 패키지/백업·강제 동기화는 같은 버전 있는 메시지 규약과 인증/권한 모델을 사용하되 메시지 종류별 허용 작업·크기·전송 제한을 구분한다. 자체 TCP/TLS/암호 알고리즘이나 임의 원격 명령 프로토콜을 만들지 않는다. 관리 웹/업무 YARP 경유로 노드 인증을 대신하지 않는다.

설치 기본값은 Unpaired이며 원격 동기화/배포 API를 활성화하지 않는다. 최초 신뢰는 양쪽 인증된 관리자 화면/로컬 설치 경로에서 공개 페어링 정보(PairId 제안, NodeId, endpoint, 인증서 공개 정보/지문, nonce, 유효기간)를 교환·검토하고 out-of-band 지문 대조 후 등록한다. 공개 정보만으로 상대를 승인하거나 네트워크에서 자동 발견한 노드를 등록하지 않는다. 초기 등록을 위해 무인증 원격 pairing API를 열지 않는다. 개인 키·평문 암호·범용 공유 관리자 비밀번호를 페어링 파일에 넣지 않는다.

등록 후 mTLS handshake로 양쪽이 개인 키 소유를 증명하고 PairId/NodeId/등록 지문·프로토콜 버전을 확인한다. 양쪽의 등록 동의와 멤버십 revision이 일치할 때만 Paired를 영속 기록하고 원격 작업을 활성화한다. 실패/만료/취소된 nonce는 재사용하지 않으며 동일 NodeId의 다른 인증서/충돌하는 페어 등록은 거부한다. 사용자 브라우저가 상대 서비스에 직접 제어 요청을 보내지 않는다.

TLS는 서버·클라이언트 양쪽 인증서의 신뢰 체인/설정한 전용 trust, 유효기간, 용도와 서버 endpoint 이름을 검증한다. 그 후 등록 PairId·NodeId·인증서 지문/공개 키 식별과 폐기 상태를 매 요청/전송 시작 시 검사한다. 같은 CA 인증서·IP allowlist·호스트명·인증서 Subject만 일치하는 것으로 통과시키지 않는다. 클라이언트 인증서는 handshake에서 필수이며 전달된 헤더의 인증서/NodeId를 신뢰하지 않는다. 미등록·만료·폐기·신뢰 확인 불가 연결은 실패 처리하고 검증 우회 설정은 제공하지 않는다.

상호 인증된 상대도 모든 권한을 갖지 않는다. 허용된 페어/솔루션의 sync·artifact transfer·관측·현재 Coordinator의 작업 명령만 수용한다. 실행 명령은 현재 세대·MembershipRevision·등록된 리소스 ID·권한/작업 단계와 대조한다. Snapshot/파일 수신은 원격 코드 실행·IIS 변경·조정 승격 권한이 아니다. 미등록 명령 종류·임의 URL/경로·다른 페어/솔루션·구세대 명령은 거부한다.

서비스는 전용 관리 인터페이스/포트에서 허용된 상대 네트워크로만 수신한다. 방화벽 제한은 mTLS를 대체하지 않는다. 관리 웹의 AD/Entra 사용자 인증, 로컬 IPC/HTTP 클라이언트 인증, 노드 간 인증은 서로 다른 신뢰 경계다. 실패 시 무인증·평문 HTTP·다른 인증 주체로 자동 fallback하지 않는다. 인증 실패/과도한 접속은 비밀 없는 보안 이벤트와 제한 정책으로 처리한다.

파일 크기/동시 전송/속도/CPU·디스크 제한은 인증된 상대에도 적용한다. 전체 파일 업로드 완료와 검증/영속 ACK를 분리하고 잘못된 chunk·전체 해시·PackageId 바꿔치기를 거부한다. 수신 중 임의 압축 해제/기동하지 않는다. 연결 재사용/TLS session 재개 상태에서도 현재 멤버십/폐기 정책으로 각 요청을 인가하고 단절·취소는 작업 ID 기준으로 재개한다.

인증서/노드 키 교체는 현재 인증된 채널과 시스템 설정 권한으로 새 공개 정보·키 소유 증명을 사전 승인하고, 제한된 이중 허용 기간 후 구키를 폐기한다. 사전 교체가 불가능한 키 유실/만료는 로컬 재페어링으로 복구하며 검증을 끄지 않는다. 페어 해제·노드 침해 시 양쪽 신뢰 목록/멤버십을 폐기하고 활성 전송·세션·작업 허가를 중단한다. 강제 동기화로 폐기된 인증서·구멤버십을 부활시키지 않는다.

감사는 PairId/NodeId/인증서 식별·허용/거부 이유·메시지/패키지/ForceSync ID·범위·시각을 기록한다. 암호·개인 키·토큰·민감한 설정 payload는 남기지 않는다. 표준 인증 구현은 [Microsoft 인증서 인증 문서](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/certauth)를 기준으로 하며 인증 성공 뒤 등록 노드 인가를 추가한다.
