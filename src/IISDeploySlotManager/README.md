# IISDeploySlotManager

> 상태: 요구사항 인터뷰를 반영한 설계 초안. 실행 프로그램, 설치 명령 및 웹 화면은 아직 구현하지 않았다.

## 목적

Windows 서버의 IIS Blue/Green 사이트를 관리하고 YARP로 운영 트래픽을 전환한다. 단독 서버와 Windows NLB 또는 기존 로드밸런서 뒤의 Active–Active 2노드 페어를 지원하는 설계다. 관리자 웹에서 초기 사이트 구성, 서버·슬롯별 검증, 암호화 패키지 배포, 설정 변환·암호화, 전환·복구·예약 작업을 관리한다. ARR과 신규 L4 장비는 요구하지 않는다.

## 구성

- Proxy: 같은 .NET 10 YARP 앱의 IIS 호스팅 / Windows 서비스 실행을 지원한다. 노드당 운영 인스턴스는 하나만 활성화한다. 마지막 적용 완료 라우팅 snapshot으로 Controller 장애 중에도 기동할 수 있다.
- Admin: 별도 관리 웹. Windows 또는 조직 Entra ID 인증을 설치 환경별로 선택한다. 업무 앱의 인증은 유지한다.
- Controller: 웹 요청 수명과 독립된 Windows 서비스. IIS/프로세스 조회·중지·한정 강제 종료, 파일 배포, 암호화, 예약, 동기화를 담당한다. 웹은 일반 권한으로 실행한다. Named Pipe IPC를 우선 사용하고 연결 불가 시 인증된 로컬 HTTP 계열 API(HTTPS)로 연결한다.
- Blue/Green: 각각 전용 폴더와 전용 App Pool을 사용한다. 별도 검증 주소는 항상 해당 슬롯을 가리킨다.
- 점검·변환·암호화 확장: 등록된 PowerShell 스크립트 또는 외부 실행 모듈을 별도 프로세스로 실행한다.
- HA 페어: 각 노드에 Proxy·Controller·Blue/Green·로컬 SQLite DB·패키지 보관소가 있다. 별도 DB 서버 없이 전용 동기화 프로토콜로 변경·패키지를 교환한다. 페어당 지정 조정 노드 하나가 배포·예약을 순차 실행하도록 조정한다. 기존 NLB/LB의 트래픽 HA를 대체하지 않는다.
- 패키지 암호: 관리자 페이지에서 암호를 입력하고 전체 패키지 검증 후 로컬 SQLite에 암호문으로 보관한다. 동기화 시 수신 노드용으로 보호된 비밀을 전달하며 예약/재배포 시 권한 있는 실행 계정만 복호화한다. 보호 키는 DB 밖에서 관리한다.
- Recovery: 웹/Controller/SQLite 장애에도 로컬 관리자가 백업 압축파일로 복원하는 별도 복구 경로다. 서비스 실행 차단·복구 잠금·RecoveryHold를 사용하며 일반 웹 권한 우회 경로로 제공하지 않는다.
- 페어링: 양쪽 관리자가 공개 인증 정보를 등록·지문 대조한 뒤 서비스 간 mTLS로 확인한다. 등록된 노드만 데이터·파일 전용 HTTPS 프로토콜을 사용할 수 있다.

## 관리자 사용 흐름

1. 솔루션 이름, 운영/Blue/Green/관리 주소, 인증서 참조, 내부 포트, 배포·보관 경로, 실행 계정 참조를 등록한다.
2. 초기 구성 계획에서 이름·포트·경로·인증서·권한 충돌과 생성 예정 리소스를 검토한다. 준비된 관리 웹과 Controller가 IIS 사이트·풀을 생성한다.
3. 한쪽 웹에 암호화 압축 패키지와 버전을 업로드하고 암호를 입력한다. 원본 파일은 상대에도 자동 업로드/동기화한다. 양쪽 파일·전체 내용·수신 비밀 검증을 통과해야 PairReady이며 미완료 상태는 화면에서 구분한다. 차등 패치에는 적용 기준 버전·파일 해시와 삭제 목록이 필요하다.
4. 현재 운영 릴리스 복구 백업과 덮어쓸 슬롯의 변경 전 백업을 압축 생성·검증한 후 대기 슬롯에 배포한다. 슬롯별 주소를 열어 수동 검증하고 자동 점검 결과를 확인한다. 백업 실패 시 배포하지 않는다.
5. 검증한 버전·설정·점검 프로필이 유지된 경우 운영 대상을 전환한다. 이전 슬롯은 롤백 기간 동안 보존한다.
6. 문제 발생 시 배포 전 백업 압축파일을 복원·점검한 뒤 전환한다. 긴급 시 트래픽을 제외·중지한 사이트에 직접 덮어쓰는 수동 복원도 지원한다. 원본 패키지로 특정 버전을 재배포하는 작업은 별도로 구분한다.
7. 선택적으로, 지정 시각 이후 업데이트되지 않은 대기 슬롯에 고정 버전을 배포하도록 예약한다. 예약 배포는 운영 전환을 수행하지 않는다.
8. 어느 노드에서든 설정 변경·업로드를 요청할 수 있다. 조정 노드가 변경 순서를 확정하고 상대가 영속 저장한 것을 확인한다. 파일/비밀까지 양쪽에서 준비되면 대기 슬롯을 배포·검증하고 한 노드씩 전환한다. 상대와 단절된 요청은 PendingSync로 보관하며 신규 페어 배포는 보류한다.
9. 데이터 불일치가 있으면 기준 서버·대상·범위를 선택하고 양쪽 DB 백업과 diff를 확인한 뒤 강제 동기화한다. 노드 전용 정보·실행 중 상태·감사 기록을 일괄 덮어쓰지 않고 과거 작업/예약은 자동 재실행하지 않는다.

## 운영 주의

Blue/Green 전환과 IIS/Windows 서비스 호스팅 전환은 별개다. 호스팅 전환은 포트·TLS 소유권 인계로 접속 공백이 생길 수 있다. 강제 종료는 해당 슬롯의 요청을 중단할 수 있다. DB·사용자 데이터 롤백과 기존 NLB/LB 자체의 HA 구성은 제공 범위 밖이다. 두 서버의 전환은 원자적이지 않으며 일시적으로 구·신버전이 함께 서비스할 수 있다.

노드 장애 시 트래픽 처리는 기존 NLB/LB의 감지·제외 구성에 의존한다. 각 노드의 DB·패키지·보호 키를 복구할 수 있어야 한다. 동기화/제어 경로 장애 시 마지막 유효 라우팅의 기존 서비스는 유지하고 신규 페어 변경은 보류한다. 단절을 상대 정지로 판단해 조정 권한을 자동 승격하지 않는다. 역할 인계는 양쪽 확인 또는 기존 노드의 실행 차단이 확인된 복구 절차로 수행한다.

Windows NLB는 앱 자체의 상태 검사를 제공한다고 가정하지 않으며 별도 감시/제외 연동을 설치 전제로 확인한다. 장애 인계 후 DegradedMaintenance는 로컬 복원·진단만 허용하고 정상 페어 재구성 전 신규 배포·예약은 보류한다. 대기 슬롯 기동의 배치·메일·큐 소비·DB 변경 억제도 앱별로 검증한다.

SQLite DB/WAL 파일을 네트워크 공유로 함께 열거나 실행 중 파일 복사로 병합하지 않는다. 설정·명령은 지정 조정 노드가 순서를 확정하고 각 노드의 관측·작업 결과는 원본 노드가 기록해 동기화한다. 로컬 계정/컴퓨터에 묶인 비밀은 수신 노드용으로 다시 보호하며 평문 암호는 동기화하지 않는다.

초기 관리 웹·Controller 설치는 로컬 설치 단계가 필요하다. 이미 실행 중인 다른 사이트를 자동으로 인수하거나 공용 풀을 강제 종료하지 않는다. 보호 파일의 OS 수동 편집 차단은 배포 보호 규칙과 별개다.
