# RECOVERY.md — IISDeploySlotManager

> 설계 단계의 운영 절차다. Recovery 실행기·CLI·웹 기능은 아직 구현하지 않았으므로 아래 설명을 현재 실행 가능한 도구로 취급하지 않는다. 정확한 명령은 구현·격리 환경 복구 시험 후 추가한다.

## 1. 상황에 맞는 경로

| 상황 | 경로 |
|---|---|
| 관리 웹/Controller 정상 | 웹에서 검증된 백업 압축파일을 선택해 복원 계획 실행 |
| 관리 웹만 장애 | 로컬 CLI에서 IPC/인증된 로컬 HTTPS로 Controller에 복원 요청 |
| Controller/관리 SQLite 장애 | 로컬 OS 관리자가 서비스 실행을 차단하고 별도 Recovery 실행기로 offline restore |
| 상대 조정 노드 장애 | 상대의 실제 변경 실행 차단 확인 후 DegradedMaintenance로 진입; 로컬 백업 복원만 허용 |
| 양쪽 공유 논리 데이터 불일치 | 소스/대상·범위를 지정한 강제 동기화; 파일 복원이나 자동 권한 승격으로 취급하지 않음 |

이전 슬롯으로 라우팅만 되돌리면 임시 트래픽 복귀다. 정식 롤백은 백업 압축파일 복원·검증을 완료한 작업으로 기록한다.

## 2. 평상시 준비

1. 각 배포에 CurrentServingRecovery와 TargetBeforeOverwrite 백업이 있는지 확인한다. 두 슬롯의 이전 버전이 다르면 백업도 다르다.
2. 백업 전체 검증 결과와 노드/솔루션/릴리스/복원 대상 manifest를 확인한다. 격리 환경에서 실제 복원 훈련을 한다.
3. 암호·키는 DB 밖의 복구 경로에서도 접근 가능하게 보관한다. 개인 키와 암호를 백업 압축파일 옆에 평문으로 두지 않는다.
4. 로컬 복구 실행기·신뢰할 manifest 검증 정보·대상 리소스 복구 설정과 저널 위치를 설치 시 마련한다.
5. NLB/LB 트래픽 제외·재편입 담당자와 확인 절차, 서비스 자동 재시작 억제 방법, 보호 파일 복원 정책을 준비한다.

## 3. 긴급 수동 롤백 순서

1. 실제 장애 노드·슬롯·운영 라우팅·릴리스를 확인하고 작업 사유·담당자를 기록한다. DB 표시만으로 현재 대상을 판단하지 않는다.
2. 신규 배포·예약·동기화 적용을 보류한다. Controller가 정상이라면 서비스에 복구 잠금을 요청한다. offline 경로에서는 서비스 중지·자동 재시작 차단·머신 전역 잠금·RecoveryHold를 확인한다.
3. 복원할 압축 백업의 종류·버전·노드·설정/키를 확인한다. 관리 DB가 손상돼도 독립 복구 메타데이터와 보안 입력/OS 키로 검증한다. 잘못된 암호·손상·신뢰 불명·복호화 불가 시 중단한다.
4. 비운영 슬롯 복원을 우선한다. 활성 사이트 직접 덮어쓰기가 필요하면 해당 트래픽을 제외하고 실제 효과를 확인한다. 접속 공백과 다른 솔루션 영향을 표시한다.
5. 대상 사이트/풀을 정상 중지하고 기한 후에도 남으면 전용 풀·PID/시작 시각·권한을 확인해 해당 프로세스만 종료한다. 공유 풀·미확인 소유권·파일 잠금이 있으면 관리자 조치 전까지 중단한다.
6. 복원 직전 상태도 새 압축 백업으로 보존한다. 실패하면 추가 데이터 손실을 피하기 위해 덮어쓰기를 시작하지 않는다.
7. 검증한 압축 내용을 격리 경로에 준비하고 파일별 추가·교체·삭제 목록을 검토한다. 새 버전의 잔여 DLL을 제거하되 Preserve·업로드·로그·타 솔루션 파일은 별도 예외 없이 변경하지 않는다.
8. 복원된 설정의 암호화 상태·키 ACL·실행 계정, Standby의 부작용 억제를 확인한 뒤 기동한다. DB 마이그레이션은 자동 실행하지 않는다.
9. 필수 점검, Proxy AppliedRevision, 해당 Proxy를 경유한 노드/슬롯/릴리스, 관찰 기준을 확인한다. 성공할 때만 운영 트래픽을 전환/재편입한다.
10. 복구 저널과 실제 상태를 현재 관리 이력에 반영한다. 관리 DB 전체를 과거 백업으로 돌려 배포/예약을 재실행시키지 않는다. 상대와 차이가 있으면 강제 동기화 계획을 따로 수행한다.
11. Controller/상대 동기화와 저널 대조가 끝날 때까지 RecoveryHold를 유지한다. 보류 예약·기존 작업을 재검토하고 승인된 것만 재개한다.

인증 우회·IIS 전체 재시작·전체 w3wp/dotnet 종료·실행 중 SQLite 파일 덮어쓰기는 복구 절차가 아니다. 복구 과정의 각 실패는 중단 지점과 실제 상태를 남기고 자동 반복 복원을 하지 않는다.

## 4. 강제 동기화 순서

1. 최신 시각만으로 기준 서버를 정하지 말고 실제 서비스 버전·변경 이력·패키지/백업 보유 상태를 대조한다.
2. SourceNodeId → TargetNodeId와 공유 데이터 scope를 지정한다. 멤버십·개인 키·노드 경로·실제 PID·감사 기록을 일괄 덮어쓰지 않는다.
3. 양쪽 변경을 보류하고 일관된 SQLite 백업·논리 snapshot을 보존한다. 실행 중 배포가 있으면 안전 지점에서 정리한다.
4. 차이와 잃게 되는 대상 변경을 확인하고 ForceSyncId·기준 sequence·SyncGeneration을 고정한다.
5. 선택된 공유 데이터를 논리 복구하고 누락된 암호화 패키지/백업·수신자 비밀을 전송한다. 중단 시 같은 ID로 재개한다.
6. 양쪽 scope의 해시·revision·참조·파일·키 검증과 수신 ACK를 확인한다. 미접속 대상을 완료로 표시하지 않는다.
7. 실제 시스템 상태 차이는 별도 적용 계획으로 다룬다. 과거 실행 허가와 복사된 예약은 보류하고 자동 재실행하지 않는다.

## 5. 완료 기록과 제한

BackupId/ForceSyncId, 대상·실측 전후 버전, 설정 범위, 수행자, 작업 사유, 중지/강제 종료, 점검·관찰, 실패/재개, 보류 예약과 남은 차이를 기록한다. 비밀값은 기록하지 않는다.

업무 DB·업로드·외부 발송 같은 부작용은 압축 백업으로 되돌아가지 않는다. 키가 없거나 앱과 DB가 호환되지 않으면 복구를 완료할 수 없다. 긴급 인플레이스 복원과 트래픽 재편입에는 접속 공백이 생길 수 있다.
