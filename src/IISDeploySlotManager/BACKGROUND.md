# IISDeploySlotManager — 개발 배경과 취지

> 기획 설명 문서. 현재는 설계 초안이며 제품 구현·실환경 검증은 완료되지 않았다. 요구사항의 기준은 [INTENT.md](INTENT.md), 세부 동작 계약은 [SPEC.md](SPEC.md)다.

## 1. 솔루션 소개

IISDeploySlotManager는 Windows IIS 환경의 웹 애플리케이션을 배포 슬롯 단위로 관리하는 운영 도구다. 운영 중인 사이트를 먼저 중지하고 파일을 교체하는 방식에서 벗어나, 대기 사이트에 배포하고 정상 동작을 확인한 뒤 사용자 요청을 전환하는 절차를 제공하려는 목적이다. 관리자 웹에서 배포·점검·설정 변경·예약·이력·백업 복원을 관리하고, 실제 시스템 변경은 Windows 서비스가 수행하도록 설계했다.

단독 서버에서 시작할 수 있고, 기존 Windows NLB 또는 로드밸런서로 서비스하는 Active–Active 두 서버를 페어로 등록해 같은 릴리스의 준비·검증·전환을 조정할 수 있다. 별도 DB 서버나 새 L4 장비를 추가하지 않고 서버별 SQLite와 인증된 서비스 간 통신을 사용한다.

## 2. 개발을 시작한 배경

현재의 출발점은 IIS 사이트 또는 App Pool을 중지한 뒤 파일을 배포하는 운영 방식이다. 파일 교체 동안 서비스 공백이 생길 수 있고, 새 버전의 기동이나 설정 오류를 운영 주소에 반영한 뒤 발견할 수 있다. 운영자가 여러 서버를 직접 오가며 같은 작업을 반복하면 서버별 버전과 설정이 달라졌는지 확인하기도 어려워진다.

초기 아이디어는 두 웹 사이트를 준비하고 사용하지 않는 사이트를 먼저 업데이트한 다음 프록시의 전달 대상을 바꾸는 방식이었다. 논의를 거쳐 YARP를 고정 진입점으로 두고 IIS Blue/Green을 교체하는 구조를 선택했다. YARP는 IIS 안에서도, 독립 Windows 서비스로도 실행할 수 있게 하며 관리 웹은 이 실행 방식과 분리한다.

추가 인터뷰에서 배포는 파일 복사만의 문제가 아니라는 점이 요구사항으로 구체화되었다. 설정 구조 변경과 암호화, 핵심 기능 검증, 프로세스 중지 권한, 압축 패치의 양쪽 서버 전달, 백업 기반 롤백, 긴급 수동 복구와 데이터 불일치 복구까지 하나의 운영 절차로 다루어야 한다.

## 3. 해결하려는 운영 문제

| 운영에서 발생하는 상황 | 제공하려는 대응 |
|---|---|
| 서비스 중지 후에야 새 버전을 배포·확인할 수 있음 | 대기 슬롯 배포와 서버·슬롯별 검증 주소 |
| 파일 복사와 설정 편집이 담당자 수작업에 의존 | 계획·변경 목록·정해진 단계·구조화된 작업 이력 |
| 버전마다 JSON/XML 설정 구조가 달라짐 | 명시된 스키마·변환 규칙으로 차이를 분석하고 모호하면 차단 |
| 운영 설정을 지키면서 암호화도 수행해야 함 | 파일 보호 정책과 솔루션별 변환·암호화 모듈 |
| 사이트/풀이 중지되지 않아 파일이 잠김 | 정상 중지·기한 확인·소유 관계 검증 후 한정 강제 종료, 권한 부족 시 알림 |
| 두 서버에 서로 다른 파일을 배포하거나 한쪽을 누락 | 한쪽 업로드의 상대 자동 복제와 노드별 검증·순차 전환 |
| 과거 버전으로 복원할 자료가 불명확 | 배포 전 검증된 압축 백업과 manifest 기반 롤백 |
| 웹 또는 관리 서비스 장애로 복구 화면을 사용할 수 없음 | 로컬 OS 관리자용 독립 복구 경로와 복구 저널 |
| 서버별 관리 데이터가 불일치 | 기준 서버·범위를 고른 강제 논리 동기화와 양쪽 사전 백업 |

## 4. 운영 방식에서 바꾸려는 점

기존 방식은 중지·복사·기동·확인의 순서에 가깝다. 목표 방식은 준비·검증·전환·관찰·복구점 보존이다. 운영 슬롯과 대기 슬롯을 구분해 사용자에게 공개하기 전에 새 릴리스를 확인하고, 전환한 뒤에도 실제 적용 버전과 핵심 기능을 관찰한다.

관리자는 실패했을 때 무엇이 바뀌었는지 알 수 있어야 한다. 따라서 접수·동기화·배포·점검·전환·완료를 구분하고, 한쪽만 성공했으면 부분 성공으로 표시한다. 요청을 보냈거나 DB 값을 저장했다는 이유만으로 배포 성공을 표시하지 않는다.

롤백의 기준도 명확히 한다. 이전 슬롯으로 트래픽만 돌리는 것은 임시 조치이며, 정식 롤백은 배포 전에 만든 백업 압축파일의 앱·지정 설정을 복원하고 검증한 결과다. 원본 패키지로 특정 버전을 다시 배포하는 작업과 백업 복원은 목적과 원본이 다르다.

## 5. 주요 사용자와 책임

| 사용자/주체 | 책임 |
|---|---|
| 운영 담당자 | 상태 조회, 패키지 등록, 점검, 배포·전환 요청과 결과 확인 |
| 시스템 설정 관리자 | 사이트/풀·인증·인증서·페어링·권한·보호 규칙·확장 모듈 관리 |
| 솔루션 개발 담당자 | 설정 스키마·변환 규칙, 대기 모드 동작, 핵심 기능 점검 프로필 제공 |
| 로컬 복구 담당자 | 웹/서비스 장애 시 대상과 백업을 확인하고 긴급 수동 복구 수행 |
| Windows 제어 서비스 | 권한·대상·작업 상태를 검사하고 시스템 변경·예약·동기화 실행 |

관리 웹은 Windows 또는 Entra ID로 인증하지만 로그인 성공이 모든 작업 권한을 뜻하지 않는다. 시스템 설정과 복구 권한은 일반 조회·배포 권한과 구분하며, 서비스도 최종 대상과 허용 작업을 다시 검사한다.

## 6. 설계의 중심 원칙

1. 운영 대상·파일 범위·프로세스 소유권이 확인되지 않으면 변경하지 않는다.
2. 파괴적 변경 전에 읽고 복원할 수 있는 백업을 확보한다.
3. 대기 슬롯도 운영 DB·큐·메일 시스템에 영향을 줄 수 있으므로 앱의 부작용 억제 계약을 확인한다.
4. 사용자 요청 처리는 관리 웹·관리 DB·동기화 장애로 불필요하게 멈추지 않도록 분리한다.
5. 인증된 상대라도 등록 페어·솔루션·작업 범위 밖의 명령은 실행하지 않는다.
6. 동기화는 백업이 아니며 상대 단절을 상대 서버 정지로 추정하지 않는다.
7. 실패를 숨기지 않고 판정 불가·권한 부족·부분 성공·복구 필요 상태를 표시한다.

## 7. 기대 효과와 확인 방법

기대 효과는 배포 중단 시간과 수동 반복 작업을 줄이고, 서버별 버전·설정 차이와 복구 절차를 명확히 하는 것이다. 현재 측정된 성능이나 중단 시간 개선 수치를 주장하지 않는다. 격리 환경에서 배포·전환·실패 주입·백업 복원·재시작·통신 단절 시험을 수행해 효과와 한계를 확인해야 한다.

성공 기준은 정상 배포 한 번에 그치지 않는다. 잘못된 암호, 설정 변환 실패, 프로세스 중지 실패, YARP 적용 거부, 상대 서버 단절, SQLite 불일치와 관리 웹 장애에서도 운영 대상이 임의로 손상되지 않고 어디서 중단됐는지 확인·복구할 수 있어야 한다.

## 8. 적용 범위와 한계

Azure App Service의 슬롯 운영과 유사한 사용 흐름을 목표로 하지만 Azure의 모든 기능이나 보장을 복제하지 않는다. 기존 NLB/LB 자체의 HA 구축, 업무 DB·사용자 업로드·외부 발송의 자동 롤백은 범위 밖이다. 두 노드의 전환은 원자적이지 않아 일시적으로 구·신버전이 함께 서비스할 수 있다.

IIS/Windows 서비스 호스팅 모드 전환과 긴급 활성 사이트 덮어쓰기는 접속 공백이 생길 수 있다. 키를 잃거나 앱과 DB가 호환되지 않으면 압축 백업이 있어도 복구가 완료되지 않을 수 있다. 두 서버의 통신 단절 중에는 신규 페어 배포를 보류하고, 관리자 확인 없는 자동 조정 권한 승격은 제공하지 않는다.
